# INFOMAN1 Prelim Lab Exam: Answers

## Task 1: Conceptual ERD Notes

The conceptual ERD in task1_conceptual_erd.drawio and its PNG export depicts four entities, namely MEMBER, TOOL, CERTIFICATION, and STORAGE_LOCATION, with underlined key attributes, connected with four verb-labeled diamonds. The borrows, requires, and completes relationships are many-to-many with the circle and crow’s foot on both ends due to the optional participation, whereas stores is one-to-many with mandatory one at the location end and a circle and crow’s foot at the tool end to signify the total participation of tools. The relationship attributes borrow_date, return_date, and completion_date are attached to the diamonds as they are left unresolved since junction tables belong to the logical model. The composite, multivalued, and derived attributes are absent as names are atomic, certification is an entity rather than a repeated attribute of tool, and the on-loan state of tools is stored as NULL return_date instead of deriving it.

## Task 2: Logical ERD and Schema Notes

The logical ERD resolves all many-to-many relationships from the conceptual model into junction tables. The borrows relationship becomes the borrowing table with a surrogate primary key borrow_id and foreign keys to member and tool. The relationship attributes borrow_date and return_date move into this table. The requires relationship becomes the tool_requirement table with a composite primary key of tool_id and cert_id. The completes relationship becomes the member_certification table with a composite primary key of member_id and cert_id plus the completion_date attribute. The stores relationship resolves into a foreign key location_code inside the tool table. Since every tool must be assigned to a location per the specification, this foreign key is mandatory. There are no weak entities or multivalued attributes to resolve in this scenario.

## Task 3: DDL Implementation Notes

I created the toolshare_prelim database and the seven tables in task3_ddl.sql. Parent tables such as storage_location, member, and certification are created before the tables that reference them. The phone column of member is a variable character (length 20) rather than number because phone numbers may begin with zero or contain symbols such as plus signs and dashes which a number column would automatically remove. The return_date column of borrowing allows NULL because a missing value means that the tool is currently on loan. The location_code column is the natural primary key of storage_location because the code A3 is a short, stable identifier that the staff is already using. All the date columns are DATE rather than DATETIME data types because the specification deals only with dates. The NOT NULL declaration on tool.location_code, and on the foreign keys of the junction tables, enforces total participation, and the FOREIGN KEY declaration on each relationship enforces referential integrity. I executed DESCRIBE on all seven tables, saving the output as task3_describe_output.txt, and checked that the columns, their data types, and key tags are as specified in Task 2.
